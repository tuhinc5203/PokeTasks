# PokeTasks Menu Bar App

## What this is
A macOS menu bar "virtual pet to-do list" built around a **collection of Gen 1 Pokémon** rather than a single fixed pet (it began life as a single Snorlax/Munchlax pet under the name "SnorlaxPet" — see the Change Log for that history and the later rename to PokeTasks). An `NSStatusItem` shows a monochrome pokeball icon (right-click for Quit and a "Launch at Login" toggle); clicking it opens an `NSPopover` that's a two-finger-swipe horizontal pager. Page 1 is the active pet: `<Name> · Lv. N` header (double-click the name to give it a nickname) + a trash button (clears completed tasks) + a refresh button (behind a confirmation dialog — permanently resets just the active pet's level), the pet's current sprite (starters begin as a shared egg at level 0, hatch to level 1 on the first completed task, evolve at species-specific levels, turn shiny permanently at level 100 — 1 completed task = 1 level, no decay), plus the same minimal drag-to-reorder task list as before. Page 2 is the "PC Box": all 3 starters (as eggs if unhatched) plus any unlocked legendaries, tap any card to make it active — doing so auto-slides the popover back to page 1. Reaching level 50 on a starter lets you pick one of Zapdos/Articuno/Moltres to unlock (tapping a locked bird card both unlocks and activates it); once all 3 birds hit level 50, Mewtwo auto-unlocks, and Mewtwo at 50 auto-unlocks Mew. A shiny (level 100) pet can be prestiged back to level 1 in its base form, permanently shiny. Completed tasks disappear from the popover 12 hours after completion, but every task ever added is permanently logged in `TodoArchive.md` at the project root. Snorlax/Munchlax were retired from the active app — their sprites just sit tidied away in their own folder, unreferenced.

## Structure
- `PokeTasks.xcodeproj` — hand-authored Xcode project (classic `PBXGroup`/`PBXFileReference` format, not Xcode 16's file-system-synchronized groups, for broad compatibility). Deployment target is macOS 14.0 (bumped from 13.0 for the collection panel's native `scrollTargetBehavior(.paging)` pager). Bundle identifier is `com.poketasks.app`.
- `PokeTasks/Assets.xcassets/AppIcon.appiconset` — the one and only asset catalog in the project (everything else uses the folder/Copy-Files approach deliberately); the app's Finder/Get Info icon, wired via `ASSETCATALOG_COMPILER_APPICON_NAME`.
- `PokeTasks/PokeTasksApp.swift` — SwiftUI `App` entry point, empty `Settings{}` scene, delegates everything to `AppDelegate`.
- `PokeTasks/AppDelegate.swift` — owns the `NSStatusItem` and `NSPopover`, click routing (left = toggle popover, right = menu), Esc-to-close, hosts `PopoverPagerView` as the popover content, prunes expired completed tasks each time the popover is about to open (no more decay to apply).
- `PokeTasks/LaunchAtLogin.swift` — thin `SMAppService.mainApp` wrapper (`isEnabled`, `setEnabled(_:)`) backing the right-click menu's checkable item.
- `PokeTasks/Model/PokemonLine.swift` — `PokemonRole` enum, `EvolutionStage` (minLevel + normal/shiny sprite names), `PokemonLine` (id, displayName, role, hasEgg, ascending stages) with `stage(for:)`/`stageIndex(for:)` lookups.
- `PokeTasks/Model/PetProgress.swift` — per-pet persisted state: `level`, `isShiny` (permanent once true at 100), `hasPrestiged` (one-time gate), `legendaryPickPending` (starter-only, set at level 50 until resolved), `nickname` (optional, user-set).
- `PokeTasks/Model/PetCollectionState.swift` — `progressByLineID: [String: PetProgress]` (presence in the dict is the sole "exists/unlocked" signal, no separate flags) + `activeLineID`.
- `PokeTasks/Model/Generations/Gen1Roster.swift` — the hand-written Gen 1 roster (3 starter lines with their real per-species evolution thresholds, 3 legendary birds, Mewtwo, Mew) plus `GenerationUnlockRules`/`Gen1UnlockRules` (live predicate: all 3 birds ≥50 unlocks Mewtwo, Mewtwo ≥50 unlocks Mew).
- `PokeTasks/Model/PetTask.swift` — the task struct (id, title, isCompleted, createdAt, completedAt, `subtasks: [Subtask]`) plus the `Subtask` struct (id, title, isCompleted). `PetTask` has a hand-written `Codable` `init(from:)` so older saved tasks that predate the `subtasks` key decode fine (defaults to `[]`) instead of failing to load.
- `PokeTasks/Model/TaskStore.swift` — persistence protocol (`loadTasks`/`save`), typed against `[PetTask]`.
- `PokeTasks/Tasks/` — `UserDefaultsTaskStore.swift` (the real `TaskStore` conformer, JSON in `UserDefaults` under `com.poketasks.tasks`, with a one-time fallback migration from the old `com.snorlaxpet.app` bundle's `com.snorlaxpet.tasks` key), `PetCollectionStore.swift` (same pattern for `PetCollectionState` under `com.poketasks.petCollection`, migrating from `com.snorlaxpet.petCollection`), `PetCollectionViewModel.swift` (the pet state machine: hatch/level-up/evolve/shiny/legendary-pick/auto-unlock, `reactionTick`/`pendingReactions` queue, `prestige(lineID:)`, `renameActivePet(to:)`/`displayName(for:)` nickname helpers), `TaskListViewModel.swift` (in-memory task list — add/rename/toggle/delete/move/prune, plus add/rename/toggle/delete for a task's subtasks, persists on every mutation — delegates all pet-leveling to `PetCollectionViewModel.registerCompletion()` from `toggleCompletion(_:)`; subtask completion is not wired to pet-leveling or the archive, it's just a nested checklist), `TaskRowViews.swift` (checkbox row with double-click-to-rename, a completed-count badge and disclosure chevron when subtasks exist, and a trailing delete "x"; expanding reveals `SubtaskRowView` rows plus an always-present add-subtask field; the always-present new-task entry row is separate, `NewTaskRowView`).
- `PokeTasks/Archive/TodoArchiveWriter.swift` — appends/updates one markdown checklist line per task in `TodoArchive.md`, keyed by a hidden `<!-- uuid -->` marker. Never deletes a line.
- `PokeTasks/Sprite/` — `SpriteBackgroundRemoval.swift` (border flood-fill background removal), `TemplateIconRenderer.swift` (opaque-and-dark-aware monochrome status-bar silhouette), `SpriteImageLoader.swift` (`loadMenuBarIcon()` plus `loadSprite(named:in: SpriteSubdirectory)` — `.root` for `Assets/Sprites`, `.gen1` for `Assets/Sprites/Gen_1` — cache key includes the subdirectory).
- `PokeTasks/Views/PetPopoverView.swift` — page 1: active pet's name/level header (double-click name to rename) + pending-legendary-pick hint, trash + confirm-gated reset buttons, sprite with wiggle/sparkle reactions driven off `PetCollectionViewModel.reactionTick`/`pendingReactions` (hatch/evolve/shiny all play the sparkle; level-up plays the wiggle), the task list.
- `PokeTasks/Views/CollectionPanelView.swift` — page 2, the "PC Box": grid of all known lines (tap to activate) plus locked bird placeholders while a legendary pick is pending (tap to unlock+activate), with a distinct cyan sparkle-burst reveal flourish on a freshly-unlocked card.
- `PokeTasks/Views/PopoverPagerView.swift` — owns the two-page `ScrollView(.horizontal)` pager's `scrollPosition` state; auto-slides back to page 1 whenever the active pet changes (selecting a pet from the PC Box, or resolving a legendary pick).
- `Assets/Sprites/Gen_1/` — 29 files (egg + 3 starter lines × 3 stages × {normal, shiny} + birds/Mewtwo/Mew × {normal, shiny}), packaged via a folder reference in the Copy Files build phase. `egg.png` is actually WebP data behind a `.png` extension — macOS `CGImageSourceCreateWithData` sniffs format from content, not extension, so this needs no special handling.
- `Assets/Sprites/Snorlax/` — the retired Snorlax/Munchlax sprites (8 files), tidied into their own folder, **not wired into the Xcode project at all** (nothing loads them).
- `Assets/Sprites/pokeball2.png` — still the menu bar icon, packaged via the same Copy Files phase; `pokeball.png` (superseded) stays on disk, unreferenced.

### 2026-08-25 — v2: pokeball icon, task list, permanent archive
- Menu bar icon switched from the Snorlax silhouette to `Assets/Sprites/pokeball.png`; the Snorlax sprite is now popover-only content. `SpriteImageLoader` was split into two independent, independently-cached loads (`loadMenuBarIcon()`, `loadPetSprite()`) instead of one combined pair.
- **Discovery during verification:** despite being an RGBA PNG, `pokeball.png` turned out to have **no real transparency at all** — every sampled pixel (including all four corners) had alpha=255, with an opaque white/off-white (238,238,238) background baked in, same problem as `snorlax_lying.png` originally had. What looked like a transparency checkerboard in an early visual check was a misread.
- Feeding the raw (opaque) pokeball image through `TemplateIconRenderer`'s old "any opaque pixel → black" rule produced a solid black disc, losing all the line-art detail — because the pokeball's white *interior* (enclosed by its outline, not touching the image border) can't be reached by `SpriteBackgroundRemoval`'s border-seeded flood fill, so it stayed opaque and then got forced to black. Fixed by changing `TemplateIconRenderer`'s rule to be luminance-aware: a pixel becomes ink only if it's **both opaque and dark**; opaque-but-light pixels now correctly become holes. This is a general fix for line-art-style template icons (a status-bar glyph with enclosed light regions), and also means `loadMenuBarIcon()` no longer needs to run `SpriteBackgroundRemoval` before generating the icon — verified by rendering the fixed pipeline on a gray backdrop and confirming a clean pokeball outline (ring, dividing line, center button) instead of a solid blob.
- Added the to-do list: `PetTask` model, `TaskStore` protocol upgraded from its `[String]` v1 stub to real `[PetTask]` load/save, `UserDefaultsTaskStore` as the first concrete conformer, `TaskListViewModel` owning add/toggle/prune. Confirmed with the user that the 12-hour completed-item cleanup only needs to run when the popover is about to open (no background timer) — the only place staleness is ever user-visible.
- Added `TodoArchiveWriter` and confirmed with the user that the archive is a **permanent, append-only record**: a task's markdown checklist line is created once (under the date it was added) and updated in place when toggled, but is never deleted — even after `TaskListViewModel` prunes it from the live list — since the entire point of an "archive" is to survive that pruning. Verified end-to-end with a standalone harness: added 3 tasks, completed one 13 hours in the past, ran the prune logic, and confirmed the live list dropped to 2 items while `TodoArchive.md` still showed all 3 with correct checkbox state. Also fixed a cosmetic bug caught by that same test — a stray blank line getting wedged mid-list when a second same-day task was appended after a freshly-created day section.

### 2026-08-26 — Global keyboard shortcut to open the popover
- Landed on **⌘⇧\\** after two rounds of back-and-forth: ⌘⇧S was rejected first (it's the near-universal "Save As…" shortcut across Mac apps — a global hotkey registered on that combo would win and steal it away from every other app system-wide, not just coexist with it), then the user picked ⌘⇧\\ directly.
- **Investigated the "proper" global-hotkey mechanism (Carbon's `RegisterEventHotKey`) before using it** — the one real advantage it has over `NSEvent` global monitors is that it doesn't require Input Monitoring permission. Checked the actual macOS 26.5 SDK headers: `RegisterEventHotKey` still exists in `HIToolbox.tbd`'s linkable symbol list but **no longer has a public header** in this SDK — meaning it'd need to be manually hand-declared to call from Swift at all. Given that fragility (an API Apple has stopped publicly exposing) versus the simplicity of the fully-public `NSEvent.addGlobalMonitorForEvents`/`addLocalMonitorForEvents` APIs, went with the latter — the one-time Input Monitoring permission prompt is a well-understood, standard trade-off for this class of app.
- Implemented as two key-down monitors registered in `applicationDidFinishLaunching` (global, for when another app is frontmost, plus local, for when SnorlaxPet's own popover already has focus), both routed through one `handlePotentialHotKey(_:)` that checks for keyCode 42 (`kVK_ANSI_Backslash`, confirmed against the real SDK header rather than assumed) with exactly Command+Shift held, then reuses the existing `togglePopover(relativeTo:)` — the same method the status-item click already uses. Compiles and builds cleanly, **but is not confirmed working end-to-end** — see below.
- **Not actually firing when tested.** Confirmed via `nm` that the shipped `/Applications` binary genuinely contains this code and that the running process started after the Input Monitoring permission was granted (so it's not a stale-build or missed-relaunch issue). Added temporary diagnostic logging (`os.Logger`, unconditionally logging every observed keyCode/modifierFlags before the match check) to get real evidence instead of guessing further — result: **zero events were ever logged**, from either monitor, even though a plain `applicationDidFinishLaunching`-reached log line *did* show up in `log show`. So logging itself works and the app does launch and reach the registration code, but neither the global nor local key-down monitor is ever invoking the handler at all. Root cause not yet found — could still be the Input Monitoring grant not actually taking effect for this ad-hoc-signed/rebuilt-each-time binary (a known trouble spot: TCC can key permission grants to a code signature that changes on every rebuild), or something else in how the monitors are registered.
- **Paused at the user's request** ("not that important right now") before finding the actual root cause. The diagnostic logging was removed and the app rebuilt/redeployed clean — the hotkey code itself is still in place (harmless if unused), just not verified functional. Pick this back up by re-adding similar logging and testing again if it becomes worth chasing.

### 2026-08-26 — Rename UX: pencil button tried, then reverted back to double-click
- User reported a noticeable delay/unreliability double-clicking a task title to rename it. Root cause: `.onTapGesture(count: 2)` inherently has to wait out the system double-click timing window to confirm a second tap is coming before it fires anything, and that's compounded by living inside the `List` adopted for drag-to-reorder — List rows have their own click/selection handling on macOS that adds another layer in front of a nested multi-tap gesture, a known SwiftUI rough edge.
- First tried removing the tap-count gesture entirely in favor of a small pencil-icon `Button` next to the delete "x" (single, unambiguous click, no latency) — but the user found the extra icon made the row feel too cluttered and asked to go back to double-click, accepting the latency instead. Reverted: pencil button removed, `.onTapGesture(count: 2)` on the title text restored. `TextField`/Enter-to-commit/Esc-to-cancel editing behavior was never touched either way.

Triggered via `.onChange(of: viewModel.wiggleTick)`, same pattern as the existing sparkle/squish triggers.

### 2026-08-26 — Pivot: single fixed pet → Pokémon collection (Pet v2)
- Replaced Munchlax→Snorlax (levels 0–6, 2-tasks-per-level, 8h decay) with a **collection of independently-leveling Pokémon**, one active at a time. Full concept worked out iteratively in `Petv2.md` before any code was touched; this entry is the implementation of that document's Gen 1 scope.
